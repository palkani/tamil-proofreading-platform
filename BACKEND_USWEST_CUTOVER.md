# Backend cutover to us-west1 (Oregon) — zero-downtime playbook

**Goal:** consolidate the two existing Cloud Run backends (`prooftamil-backend` in asia-south1 + `prooftamil-backend-us` in us-central1) into a single new service `prooftamil-backend-uswest` in **us-west1** (Oregon, colocated with the Supabase database in us-west-2 Oregon).

**Why:** the Asia backend was paying ~250ms cross-Pacific latency per DB query. Colocating the backend with the DB cuts DB-query latency from ~250ms → ~5ms per query, which makes ALL users faster — including Indian users — once a request makes more than one DB call. See the [architectural rationale](#architectural-rationale) at the bottom.

**Risk profile:** strict zero-downtime. The PR that adds the new service does NOT change any user-facing traffic. Old services keep running unchanged. The cutover is a single Vercel environment-variable update, atomic and reversible in <30 seconds.

## Phase 1 — Merge the PR (no traffic change)

Merging the PR triggers the existing deploy workflow, which now does three things instead of two:

1. Deploys to `asia-south1` (`prooftamil-backend`) — unchanged.
2. Deploys to `us-central1` (`prooftamil-backend-us`) — unchanged.
3. **New:** deploys to `us-west1` (`prooftamil-backend-uswest`) — parallel, no traffic.

The workflow's first run for us-west1 will:
- Create an `us-west1` Artifact Registry repository named `docker-repo` (one-time, idempotent).
- Tag and push the backend image to the us-west1 registry.
- Create the Cloud Run service `prooftamil-backend-uswest` with `min-instances=1`, `cpu=2`, `memory=2Gi`, the same env vars and secrets as the other two services.

**Watch the workflow run.** The "Verify Backend Health (All Regions)" step at the end prints all three URLs, including a line:

```
>>> Copy this URL for the Vercel cutover (see BACKEND_USWEST_CUTOVER.md)
```

**Copy that us-west1 URL.** Format will be something like `https://prooftamil-backend-uswest-XXXXXXXX-uw.a.run.app` (the XXXXXXXX is auto-generated by GCP).

**Verify nothing user-facing changed:** Vercel still routes per the existing `BACKEND_URL_ASIA` / `BACKEND_URL_US` env vars. Users continue hitting the old two services.

## Phase 2 — Smoke-test the new service (5 minutes, before any cutover)

Run these against the new us-west1 URL you just copied. Replace `<URL>` with the actual URL.

```bash
# 1. Service is reachable
curl -sS -o /dev/null -w "health: %{http_code} %{time_total}s\n" <URL>/health

# 2. DB connectivity — public blog endpoint should return real posts
curl -sS "<URL>/api/v1/blog/posts?page=1&limit=3" | python3 -m json.tool | head -20

# 3. Auth endpoint correctly rejects an invalid token (= DB query path works)
curl -sS -o /dev/null -w "auth: %{http_code}\n" -X POST \
  -H "Content-Type: application/json" \
  -d '{"access_token":"not-a-real-token"}' \
  <URL>/api/v1/auth/supabase-token
# Expect: 401 (unauthorized) — NOT 500, NOT 503

# 4. Compare blog-list output byte-for-byte to existing US service
diff \
  <(curl -sS "<URL>/api/v1/blog/posts?page=1&limit=3" | python3 -m json.tool) \
  <(curl -sS "https://prooftamil-backend-us-991187041222.us-central1.run.app/api/v1/blog/posts?page=1&limit=3" | python3 -m json.tool)
# Expect: zero output (= identical responses)
```

If any of these fails, **STOP**. Check the Cloud Run logs for `prooftamil-backend-uswest` in the GCP console. Common first-deploy issues:
- Secret not granted to the new service's service account → add IAM binding.
- `gcloud artifacts repositories create` failed silently → run the command manually with `--no-quiet`.

Do NOT proceed to Phase 3 until all four smoke tests pass.

## Phase 3 — Vercel cutover (the atomic moment)

This is the actual traffic switch. **It takes ~10 seconds. It is reversible in <30 seconds.**

**Vercel dashboard → tamil-proofreading-platform → Settings → Environment Variables.**

For each of `Production`, `Preview`, and `Development` environments:

| Variable | Current value | New value |
|---|---|---|
| `BACKEND_URL_ASIA` | `https://prooftamil-backend-991187041222.asia-south1.run.app` | `<new us-west1 URL>` |
| `BACKEND_URL_US` | `https://prooftamil-backend-us-991187041222.us-central1.run.app` | `<new us-west1 URL>` |
| `BACKEND_URL` (fallback) | (existing) | `<new us-west1 URL>` |

**Both regional vars now point at the same new us-west1 URL.** This means Express's regional-routing logic still runs but both branches lead to the same place — which is exactly what we want. No code change needed in Express for this phase.

After updating the env vars, **trigger a Vercel redeploy** (Settings → Deployments → ⋯ → Redeploy on the latest production deployment, or push any tiny change to main). Env var changes only take effect on a fresh deploy.

Wait for the redeploy to finish (~1-2 minutes).

You can also check Cloud Run metrics in the GCP console — `prooftamil-backend-uswest` request count should be ticking up while `prooftamil-backend` and `prooftamil-backend-us` request counts go to zero.

## Phase 5 — Monitor for 24-48 hours

**During the monitoring window, leave the old services running.** They cost ~nothing at min-instances=0 and serve as a one-command rollback.

Things to watch:
- **GCP Cloud Run console** → `prooftamil-backend-uswest` → Metrics: request count up, request latency in normal range, no spike in 5xx errors.
- **Vercel logs**: search for `[backend-retry]` or `[BLOG]` lines — should see normal traffic, no error spikes.
- **Microsoft Clarity / Speed Insights**: LCP for the homepage may improve (faster DB hop). Watch for ~24h after cutover.
- **Synthetic monitor (GitHub Actions)**: the existing hourly synthetic monitor still works — it hits `https://www.prooftamil.com/...`, which now goes via Express → us-west1 backend.

### Rollback (if anything looks bad)

Revert the Vercel env vars to their original values + redeploy. The old services are still running and will resume serving traffic immediately. **Total rollback time: ~2 minutes.**

```
BACKEND_URL_ASIA → https://prooftamil-backend-991187041222.asia-south1.run.app
BACKEND_URL_US   → https://prooftamil-backend-us-991187041222.us-central1.run.app
BACKEND_URL      → (whatever the original was)
```

## Phase 6 — Decommission the old services (after 24-48h of clean monitoring)

Once you're confident the new service is solid, free up the old infrastructure:

### Step 6.1 — Add an UptimeRobot monitor for the new service

(Optional but recommended.) In UptimeRobot, add an HTTP monitor pointing at `<new us-west1 URL>/health`, 5-min interval, **HTTP method GET** (we discovered earlier that the backend returns 404 on HEAD). This keeps your monitoring continuity.

Then **delete** the two existing UptimeRobot monitors for the old asia-south1 and us-central1 services.

### Step 6.2 — Delete the old Cloud Run services

```bash
gcloud run services delete prooftamil-backend     --region=asia-south1 --quiet
gcloud run services delete prooftamil-backend-us  --region=us-central1 --quiet
```

This stops billing for the old services immediately. The container images stay in Artifact Registry (you can clean those up too, but they're cheap to leave).

### Step 6.3 — Open the follow-up PR (cleanup)

A second PR cleans up the now-unused infrastructure code. I recommend keeping it as a separate PR so the cutover and the cleanup are clearly bisectable.

The follow-up PR should:

1. **Remove the two old deploy blocks** from `.github/workflows/deploy.yml` (keep only the us-west1 block).
2. **Update the health-check step** to verify only the us-west1 service.
3. **Simplify `express-frontend/utils/regional-backend.js`** from 115 lines to ~10. Replace the geo-routing logic with a single `getBackendUrl()` that returns `process.env.BACKEND_URL`. The exported `getPrimaryBackendUrl` can become an alias.
4. **Remove `BACKEND_URL_ASIA` and `BACKEND_URL_US`** from Vercel env vars (Settings → Environment Variables → delete). Keep only `BACKEND_URL`.

If you want me to ship that PR, ask after you've completed Phase 6.2.

## A note on the runner services

The transliterator runner services (`prooftamil-runner` + `prooftamil-runner-us`) follow the **opposite** geographic rule from the backend: they're stateless ML inference, they don't talk to Supabase, and Indian users make many rapid requests to them (Tanglish typing in the editor). For runners, **user proximity matters more than data proximity** — `asia-south1` is the right region for the Indian audience.

So:
- Backend → us-west1 (this cutover)
- Runner → stays in asia-south1 (no change)

If you also have `prooftamil-runner-us`, that one is the wasted twin to delete in a separate small PR.

## Architectural rationale

For an Indian user making one API request with N DB queries:

| Path | TLS (once) | DB query (×N) | Total for N=2 |
|---|---|---|---|
| `asia-south1` backend + us-west-2 DB (today) | ~50ms | ~250ms cross-Pacific | **~550ms** |
| `us-west1` backend + us-west-2 DB (after cutover) | ~250ms cross-Pacific | ~5ms intra-Oregon | **~260ms** |

The DB query cost is paid N times. The TLS handshake is paid once (HTTP keep-alive). Past N≥1, the colocated backend wins.

The general SRE rule: **put compute next to data, not compute next to users.** The CDN/edge handles user proximity (Vercel does that for ProofTamil). The backend's job is to talk to the DB efficiently.
